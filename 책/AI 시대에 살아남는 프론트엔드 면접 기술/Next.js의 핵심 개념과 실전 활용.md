- Next.js를 사용하는 이유
  - SSR과 SSG
    - SSR은 완성된 HTML을 생성하여 전송, 검색 엔진 크롤러가 컨텐츠를 쉽게 수집, 빠르게 웹 사이트를 확인 가능
    - SSG는 빌드 시점에 HTML을 미리 생성해 배포하여 가장 빠른 로딩 속도, ISR 을 지원하여 주기적으로 콘텐츠 갱신
  - 폴더(App Router) & 파일(Pages Router) 기반 라우팅 (폴더가 더 최신)
    - 간편하게 라우트 구성
  - API Rroutes
    - 별도의 백엔드 서버를 구축하지 않고도 서버 쪽 로직을 함께 구현할 수 있다.
    - CORS 설정의 복잡함을 줄일 수 있다.
  - 이미지 최적화
    - 이미지를 자동으로 최적화하여 제공
    - 이미지 크기를 미리 계산해 렌더링 하여 레이아웃 밀림 현상도 방지 가능
- CSR, SSR, SSG
  | **구분**                   | **CSR (Client-Side Rendering)**           | **SSR (Server-Side Rendering)**                  | **SSG (Static Site Generation)**            |
  | -------------------------- | ----------------------------------------- | ------------------------------------------------ | ------------------------------------------- |
  | **렌더링 위치/시점**       | **브라우저(클라이언트)** / 런타임         | **서버** / **요청 시점(사용자 접속 시)**         | **서버/빌더** / **빌드 시점(배포 전)**      |
  | **초기 로딩 속도 (FCP)**   | 상대적으로 느림 (빈 HTML 수신 후 JS 실행) | 빠름 (완성된 HTML 즉시 표시)                     | **가장 빠름** (미리 완성된 HTML + CDN 캐싱) |
  | **페이지 이동 속도**       | 빠름 (필요한 데이터만 JSON 수신)          | 매 이동마다 서버 요청 시 상대적으로 느릴 수 있음 | 빠름 (SPA 방식 전환 가능)                   |
  | **서버 부하**              | 매우 낮음 (정적 파일 호스팅)              | 트래픽 증가 시 서버 연산 부하 발생               | 매우 낮음 (CDN 정적 서빙)                   |
  | **데이터 최신성**          | 항상 최신 (클라이언트 API 호출)           | **항상 최신** (요청마다 실시간 DB/API 조회)      | 빌드 시점 데이터 (재빌드 또는 ISR 필요)     |
  | **SEO (검색 엔진 최적화)** | 취약 (JS 실행 못하는 크롤러 대상)         | **매우 우수**                                    | **매우 우수**                               |
- 앱 라우터와 페이지 라우터
  | **구분**                | **Pages Router (페이지 라우터)**                    | **App Router (앱 라우터)**                                      |
  | ----------------------- | --------------------------------------------------- | --------------------------------------------------------------- |
  | **기본 컴포넌트**       | Client Component (전통적인 React 컴포넌트)          | **React Server Component (RSC)** (기본 서버 렌더링)             |
  | **라우팅 매핑**         | **파일 이름** 기준 (`pages/about.js` → `/about`)    | **폴더 이름** 기준 (`app/about/page.js` → `/about`)             |
  | **레이아웃 구조**       | `_app.js` 또는 페이지별 `getLayout` 수동 구현       | `layout.js` 파일을 통한 **자동 중첩 레이아웃(Nested Layout)**   |
  | **데이터 패칭 방식**    | `getServerSideProps`, `getStaticProps` 등 전용 함수 | 표준 `fetch()` API (캐싱/재검증 옵션) 및 `async/await` 컴포넌트 |
  | **로딩 / 에러 처리**    | 상태(state)로 수동 제어                             | `loading.js`, `error.js` 등 특수 파일로 선언적 처리             |
  | **스트리밍(Streaming)** | 지원 제한적                                         | React `Suspense` 기반 점진적 스트리밍 SSR 완벽 지원             |
  - 앱 라우터를 사용하는 이유
    - **서버 컴포넌트**
      - 앱 라우터의 핵심으로, 서버에서 렌더링되고 실행되는 리액트 컴포넌트
      - 클라이언트로 전송되는 번들에 포함되지 않으므로 번들 크기를 줄이고 초기 로딩 성능을 높일 수 있다.
      - `async/await` 문법을 사용하여 직접 데이터를 패칭할 수 있어서 `getServerSideProps`나 `getStaticProps`같은 별도의 페칭 함수를 작성할 필요 없다.
      - 서버 리소스에 직접 접근 가능하다.
      - 브라우저와 상호작용을 위해서는 `‘use client’` 지시어를 명시해 클라이언트 컴포넌트로 전환하면 된다.
    - **스트리밍**
      - 서버 컴포넌트와 함께 동작하는 Next.js의 중요한 렌더링 기능
      - 준비된 부분부터 순차적으로 클라이언트에 전송
      - 리액트의 Suspense컴포넌트와 함께 사용하면 특정 컴포넌트의 데이터를 기다리는 동안에도 다른 UI 요소를 상호작용할 수 있어 사용자 경험이 크게 향상된다.
    - **중첩 레이아웃**
      - 여러 페이지에서 반복되는 UI코드를 한곳에서 관리 가능
      - 불필요한 렌더링을 줄여 성능 향상
    - 이외
      - loading.js파일 기반 로딩 UI
      - error.js 파일 기반 오류 경계
      - 발전된 Metadata API
- 서버 컴포넌트와 클라이언트 컴포넌트
  - **하이드레이션**
    - 서버에서 미리 만들어 보낸 정적 HTML에 브라우저가 다운로드한 JavaScript를 결합하여 클릭, 입력 등이 가능한 **인터랙티브한 웹 페이지로 만드는 과정**입니다.
    - **서버 컴포넌트는 하이드레이션 과정이 생략**되므로, 브라우저가 다운받고 실행해야 할 JS 양이 대폭 줄어들어 웹 속도가 빨라진다.
  | **구분**          | **서버 컴포넌트 (RSC)**                                                    | **클라이언트 컴포넌트 (RCC)**                                          |
  | ----------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
  | **선언 방식**     | 기본값 (아무것도 안 적으면 RSC)                                            | 최상단에 `'use client'` 선언                                           |
  | **실행 위치**     | **오직 서버**에서만 실행                                                   | **서버(초기 HTML 프리렌더링) + 브라우저**                              |
  | **JS 번들 크기**  | 클라이언트 JS 번들에 **포함 안 됨 (0KB)**                                  | 클라이언트 JS 번들에 **포함됨**                                        |
  | **가능한 작업**   | DB 직접 조회, 비밀키(API Key) 안전 사용, 무거운 라이브러리 사용            | 상태 관리(`useState`), 생명주기(`useEffect`), 이벤트 리스너(`onClick`) |
  | **불가능한 작업** | `useState`, `useEffect`, `onClick`, 브라우저 API(`window`, `localStorage`) | `async` 컴포넌트 자체 직접 사용(Next 15 기준 제한적), 보안키 직접 접근 |

- Next.js의 라우팅 시스템
  - page 라우터
    - 12버전 이하에서 사용되던 방식
    - pages 디렉터리 내의 `.js`, `.jsx`, `.ts`, `.tsx` 파일이 하나의 라우터가 되어 파일 구조가 곧 URL 구조로 연결된다.
  - app 라우터
    - 13버전 이상에서 사용되는 방식
    - 폴더가 URL 경로를 결정하고 그 안의 page.js가 실제 페이지를 담당
  - next/link 컴포넌트
    - 클라이언트 사이드 네비게이션
      - 브라우저의 전체 새로고침 없이 JS를 통해 돔만 부분적으로 업데이트하는 방식으로 페이지를 전환
      - HTML을 통째로 다시 만드는 대신, 바뀐 부분에 대한 데이터만 받아와 브라우저의 리액트가 DOM을 부분 교체한다.
    - 링크 프리페칭
      - 사용자가 특정 Link 컴포넌트가 포함된 영역을 스크롤하여 뷰포트에 진입하거나 마우스를 링크 위에 올리면 Next.js가 해당 링크가 가리키는 페이지의 JS 번들을 미리 내려받아 캐시에 저장한다.
    - Link 컴포넌트와 useRouter 훅의 사용
      - Link 컴포넌트는 선언적 방식
      - useRouter 훅은 프로그래밍 방식
- Next.js의 하이드레이션 오류
  - **서버가 전달한 HTML의 내용과 클라이언트에서 JS(React)가 렌더링하려고 기대한 결과물이 서로 다를 때 발생한다**.
    - window, localStorage 등 브라우저에만 있는 API를 사용할 때
    - `new Date()`, `Math.random()` 처럼 실행 시점에 따라 결과가 바뀔 때
    - 부정확한 HTML 구조일 때. <p>태그 안에 <div>를 넣는 등 HTML 규칙에 맞지 않게 작성하면
  - 오류 해결 방법 - 3가지
    - `useEffect` 활용
      - `useEffect` 훅은 하이드레이션이 끝난 후 클라이언트에서만 실행된다.
      - 브라우저 API를 `useEffect` 안으로 옮긴다. (`window.innerWidth`)
    - next/dynamic으로 컴포넌트 분리
      - dynamic import를 사용하고 `ssr: false` 옵션을 준다.
    - `suppressHydrationWarning` 속성 사용
      - 시간을 보여주는 부분처럼 매번 바뀌는 값에 쓴다.
      - 남용하면 UI가 이상하게 보일 수 있어서 꼭 필요할때만 쓴다.
- Next.js에서 API 루트를 사용하는 목적
  - API 루트는 특정 디렉터리 내에서 JS 파일을 생성하는 것만으로 해당 파일이 HTTP API 엔드포인트 역할을 하도록 만드는 기능
    - 프런트엔드와 백엔드 로직 통합
    - 서버리스 함수 지원 : 필요한 순간에만 쪼개진 단위로 실행된다. (요청이 있을 때만 서버 자원 사용)
    - 클라이언트-서버 간의 ‘미들웨어’ 역할 : CORS, 보안 문제 등으로 클라이언트에서 직접 외부 API를 호출하기 어려운 상황에서 중간 다리, 즉 프록시 역할을 수행한다.
  - pages/api 디렉터리 내에 파일을 만들면 해당 파일이 API 엔드포인트가 된다.
  - API 루트의 장점과 단점
    - 장점
      - 풀 스택 개발 용이성
      - 서버리스 배포
      - 보안 강화 : API 루트는 서버 환경에서 실행되므로 민감한 정보를 안전하게 다룰 수 있다.
      - CORS 문제 해결 : 프런트엔드와 백엔드가 같은 도메인에 있는 것처럼 동작한다.
    - 단점
      - 복잡한 백엔드 로직에는 부적합 : 대규모, 복잡한 비즈니스 로직과 실시간 처리가 필요한 경우, 전통적인 독립형 백엔드 서버가 더 적합하다.
      - 콜드 스타트 : 서버리스 함수의 특성상 오랜 시간 호출되지 않았다가 다시 호출될 때 초기 시작 지연이 발생한다.
      - Next.js에 종속적

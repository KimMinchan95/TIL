- 가상 돔과 재조정 과정의 역할
  - 가상돔
    - 실제 돔을 직접 조작하는 작업은 비용이 큰 작업이다.
    - 리액트는 가상 돔이라는 자바스크립트 객체 형태의 가벼운 표현을 돔과 유사한 구조로 만든다.
    - 가상 돔과 실제 돔을 비교해 변경된 부분만 실제 돔에 반영하는 재조정을 통해 돔 조작을 최소화한다.
  - 재조정
    - 리액트가 UI를 효율적으로 업데이트하기 위해 수행하는 핵심 알고리즘
    - 단계
      - 렌더링 발생 → 비교 알고리즘 → 배치 업데이트 → 실제 돔 업데이트
  - 가상 돔과 재조정 과정의 역할
    - 불필요한 실제 돔 조작 최소화
    - 선언적인 UI 작성
    - 플랫폼 독립성 제공
    - 배치 업데이트를 통한 효율적인 렌더링 제공
  - 파이버 객체
    - **컴포넌트 하나에 대한 정보를 담고 있는 JS 객체**
    - 4개의 작업 스케줄을 반복하면서 각 노드의 일을 처리
      - beginWork(): 현재 파이버를 기준으로 자식 파이버를 생성하거나 갱신
      - completeWork(): 자식 파이버들의 처리가 끝난 뒤 호출, 실제 돔 변경을 위한 준비 작업
      - performUnitOfWork(): 하나의 작업 단위 실행하면서 하위 노드 내려가 작업을 이어간다.
      - completeUnitOfWork(): 더 이상 처리할 자식이 없을 때 노드를 올라가면서 작업을 완료하고 형제 파이버로 이동하도록 처리
    - 파이버는 연결 리스트 구조로 이어져 있어 재귀 호출 없이도 전체 컴포넌트 순회가 가능하다.
  - 파이버의 2단계 작동 원리
    - 렌더 단계
      - 리액트가 변경이 필요한 컴포넌트를 파악하여 새로운 파이버 트리를 구축 (work-in-progress tree)
      - 이전 파이버 트리와 새로운 트리를 비교해 어떤 돔 변경이 필요한지 계산 (effect list를 만듬)
      - 비동기적으로 진행되고 필요하면 언제든 중단할 수 있다.
    - 커밋 단계
      - effect list를 가져와 정리된 모든 변경 사항을 실제 돔에 swap 방식으로 한 번에 적용
      - 동기적으로 실행되며 중간에 멈출 수 없다.

- 리액트 성능 최적화를 위한 방법
  - 메모리제이션 기법
    - 함수의 연산 결과를 저장해 두었다가 같은 입력이 들어오면 다시 계산하지 않고 저장된 값을 재사용하는 기법
  - 컴포넌트 메모이제이션 - React.memo
    - 고차 컴포넌트로, 렌더링 결과가 동일한 컴포넌트를 메모이제이션하여 props가 변경되지 않는한 리렌더링 방지
    - props가 들어오면 얕은 비교를 해서 동일하다면 리렌더링하지 않고 마지막 렌더링 결과 재사용
  - 함수 메모이제이션 - useCallback
    - 처음 렌더링될 때 함수를 생성하고 의존성 배열 값이 변경되지 않았다면 이전에 생성한 함수를 재사용
  - 값 메모이제시션 - useMemo
    - 특정 의존성이 변경되지 않는 한 값을 다시 계산하거나 새로운 참조를 생성하지 않도록 함
  - **앱 로딩 시간 개선**
    - 코드 스플리팅과 지연 로딩
      - 코드 스플리팅은 앱의 모든 코드를 하나의 큰 번들 파일로 만드는 대신 필요한 시점에 필요한 코드만 로딩하도록 번들을 여러 개의 작은 파일로 나누는 기법
      - `React.lazy`와 `Suspense`를 사용하면 컴포넌트가 필요할 때 동적으로 컴포넌트를 로드할 수 있다.
      - `import`구문을 사용하여 특정 모듈을 필요할 때 비동기적으로 가져온다.
  - **이미지 최적화**
    - 적절한 이미지 형식: JPEG(사진), PNG(투명 배경), Webp/AVIF(차세대 포맷, 높은 압축률) 사용
    - 이미지 압축
    - 반응형 이미지: <picture>태그나 srcset 속성을 사용하여 기기 해상도에 맞는 최적의 이미지 제공
    - 지연로딩: loading=”lazy” 속성을 사용하여 이미지가 뷰포트에 들어올 때 까지 로딩 지연
    - CDN: 이미지와 같은 정적 자산을 사용자에게 더 가까운 서버에서 빠르게 전송
  - **번들러 최적화**
    - 트리 셰이킹: 사용되지 않는 코드를 최종 번들에서 제거
    - Minification & Uglification: 코드의 불필요한 공백, 주석 등을 제거하고 변수 이름을 짧게 변경해 파일 크기를 줄인다.
    - 캐싱 전략: 브라우저 캐싱을 활용하여 재방문 시 빠르게 리소스 로드

- 리액트 18버전에 도입된 동시성 기능
  - **여러 개의 UI 업데이트 작업을 동시에 처리하고 각 업데이트의 우선순위를 지정하여 관리할 수 있는 새로운 기능**
    - 사용자 경험 개선: UI가 항상 반응성을 유지하도록 하여 무거운 업데이트가 진행 중일 때도 사용자 입력이 끊기지 않고 즉시 피드백을 받을 수 있게
    - 업데이트 우선 순위 관리
    - 중단 가능한 렌더링: 중요한 작업이 발생하면 렌더링 작업을 중단하고 먼저 처리한 후, 중단했던 렌더링 작업을 나중에 다시 시작
  - **startTransition**
    - **긴급하지 않은 UI 업데이트를 트랜지션으로 지정**
    - `const [isPending, startTransition] = useTransition();`
      - `useTransition`은 매개변수를 받지 않는다.
      - `isPending` 플래그는 대기중인 Transition이 있는디 알려준다.
      - `startTransition` 함수는 업데이트를 Transition으로 표시할 수 있게 해주는 함수
      ```jsx
      const [input, setInput] = useState("");
      const [query, setQuery] = useState("");
      const [isPending, startTransition] = useTransition();

      const handleChange = (e) => {
        // 1. 긴급한 UI 변경
        setInput(e.target.value);

        // 2. 덜 긴급한 UI 변경 (직접 래핑)
        startTransition(() => {
          setQuery(e.target.value);
        });
      };
      ```
  - **useDeferredValue**
    - **특정 값의 업데이트를 지연**(defer)시켜 해당 값이 사용되는 UI 부분의 렌더링을 덜 급하게 처리할 수 있다.
    - 값으로 받은 값이 업데이트 되더라도 긴급한 업데이트가 모두 처리된 후에 업데이트 된다.
    ```jsx
    **function SearchResults({ query }) {
      // 부모로부터 받은 props(query)를 지연된 값으로 생성
      const deferredQuery = useDeferredValue(query);
      const isStale = query !== deferredQuery; // 로딩 상태 직접 판별

      // deferredQuery를 사용해 무거운 작업 수행
      const list = heavyCalculation(deferredQuery);

      return (
        <div style={{ opacity: isStale ? 0.5 : 1 }}>
          {list.map(item => <Item key={item.id} data={item} />)}
        </div>
      );
    }**
    ```
- 리액트 컴포넌트의 오류 처리
  - 리액트 16버전에 도입된 에러 바운더리 사용
  - **하위 컴포넌트 트리에서 발생한 JS 오류를 감지하고 대체 UI(fallback UI)를 보여 줄 수 있게 하는 컴포넌트**
    - 이벤트 핸들러 내부에서 발생하는 오류는 렌더링 단계와 분리되어 실행되므로 `try~catch`로 직접 처리
    - `setTimeout`, `requestAnimationFrame`, 프로미스트 `then`, `catch`같은 비동기 코드도 감지하지 못함
    - SSR 과정에서 발생한 오류, 에러 바운더리 컴포넌트 자신에서 발생한 오류는 무한루프를 방지하기 위해 에러 바운더리가 포착하지 않는다.
  - **에러 바운더리 구현 조건**
    - 반드시 클래시 컴포넌트로 구현해야 한다.
    - 2가지 생명주기 메서드 중 하나 또는 둘 다를 구현해야 한다.
      - `static getDerivedStateFromError(error)`: 하위 컴포넌트에서 오류가 발생했을 때 호출되며 오류 정보를 받아 상태를 업데이트하고 다음 렌더링에서 대체 UI를 표시하도록 준비하는 역할을 한다. `static` 메서드 이므로 `this` 에 접근할 수 없으며 반드시 상태 객체를 반환해야 한다.
      - `componentDidCatch(error, errorInfo)`: 하위 컴포넌트에서 오류가 발생했을 때 호출되며 오류 정보를 외부 로깅 서비스에 전송하는 등 부수 효과를 처리하는 데 사용된다. `error`는 발생한 오류 객체이며 `errorInfo`는 `componentStack` 속성을 포함하여 오류가 발생한 컴포넌트 스택 정보를 담고있다.
- CSR의 개념과 한계점
  - CSR의 개념
    - 웹 페이지의 화면을 서버가 아닌 클라이언트, 즉 브라우저에서 자바스크립트를 사용해 그리는 방식
  - CSR의 한계점
    - **검색 엔진 최적화(SEO) 문제**
      - 초기 HTML에 실제 컨텐츠가 거의 없고, 화면 내용이 자바스크립트가 실행된 후 동적으로 생성
      - 구글의 최신 검색 엔진은 JS를 실행할 수 있지만 렌더링이 완료될 때까지 추가 시간이 필요하므로 검색 엔진 최적화 측면에서 불리하다.
    - **사용자 경험 저하**
      - JS가 내려받아지고 실행되기 전까지 Blank Page가 나타날 수 있고, 처음으로 의미 있는 콘텐츠를 보게 되는 시점인 FCP(First Contentful Paint)가 지연된다.
      - 상호작용 가능한 상태가 되기 전까지 오래걸릴 수 있어서 TBI(Total Blocking Time)와 TTI(Time To Interactive)가 길어질 수 있다.
    - **보안 취약점**
      - API 키나 데이터베이스 접근 정보 등을 클라이언트 사이드 코드에 직접 포함할 경우 쉽게 노축ㄹ된다.
      - 서버에서 API를 프록시하는 방식으로 해결할 수 있지만 CSR환경에서는 보안 설계에 특히 신경써야한다.
- key 속성의 중요성과 정확한 사용법
  - 각 항목을 구분하기 위해 사용하는 특별한 속성이다.

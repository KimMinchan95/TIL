- 프로젝트 빌드와 배포
  - 지속적 통합(CI) - 버그가 있는 코드가 통합되는 것을 조기에 막아주는 품질 관리 단계
  - 지속적 배포(CD) - 검수를 마친 제품을 자동으로 build해 시장에 내놓는 출시 단계
  - 프론트의 CI/CD
    - 번들링 최적화 - 비트, 웹팩 같은 번들러로 모듈들을 합치고 코드를 압축, 제거한다.
    - 품질 일관성 유지 - ES Lint로 코드 스타일 통합, Prettier로 포맷을 맞추고 제스트로 컴포넌트 단위 품질 테스트 진행
    - 빠른 피드백과 배포 - git push 한 번으로 모든 과정을 자동화하여 다음 작업에 집중할 수 있게 한다.
- ES 모듈과 CommonJS 모듈의 차이점
  - CommonJS 묘듈
    - 파일 단위로 코드를 나누고 불러오기 위한 모듈 시스템, 주로 Node.js 환경에서 사용
    - 동기적으로 작동, `require()` 를 호출하면 해당 파일을 즉시 찾고 실행하고, 다음 결과를 반환할 때까지 다음 코드 실행을 멈춘다.
  - ES 모듈(ESM)
    - JS의 공식 모듈 시스템
    - 브라우저와 Node.js 모두 지원
    - 비동기적으로 작동하면 정적 구조를 가진다.
    - `import` 문을 통해 필요한 모듈 목록을 먼저 파악하고 이를 비동기적으로 때로는 병렬로 불러온다.
  - 두 모듈의 차이: 트리셰이킹
    - ESM의 `import`는 정적이어서 웹팩 같은 번들러가 빌드 시점에 코드를 분석할 수 있다.
      - 사용되지 않은 함수는 최종코드에서 제외한다.
    - CommonJS는 동적인 함수 호출이어서 트리 셰이킹이 불가능하다.
  - 트리 셰이킹과 배럴 파일
    - 배럴 파일은 디렉터리 안의 여러 모듈을 모아 한꺼번에 `export`하는 역할을 한다.
    ```jsx
    export * from "./Button";
    export * from "./Input";
    export * from "./Modal";
    ```

    - 배럴 파일은 모듈 간의 관계를 모호하게 만들어 번들러가 과감하게 코드를 제거하지 못하게 막는다.
      - CSS파일은 `import` 하는 것 자체가 의미를 가지는 경우가 있어서 예외를 처리하면 트리 셰이킹에 도움을 줄 수 있다.
        ```jsx
        {
        	"name": "project",
        	"version": "1.0.0",
        	"sideEffects": [
        		"**/*.css",
        		"**/*.scss"
        	]
        }
        ```
- 번들러를 사용하는 이유
  - script 태그로 JS파일을 하나씩 불러올 때의 단점
    - 네트워크 병목 현상 - script 태그 만날 때마다 서버에 파일 요청
    - 복잡한 의존성 관리
    - 불필요한 코드 로딩 - 하나의 함수만 필요하더라도 파일 전체를 내려받는다.
  - 번들러는 여러 개로 나뉜 코드 조각을 분석해서 브라우저가 가장 효율적으로 처리할 수 있는 몇 개의 파일로 합치는 역할
  - 번들링 과정에서 이뤄지는 최적화
    - 번들링 - HTTP 요청 수를 줄여서 네트워크 병목 현상 완화, 초기 로딩 속도 크게 향상
    - 트랜스파일링
    - 코드 최소화
    - 코드 분할
  - 번들러의 의존성 그래프
    - 아래 과정으로 연결된 모든 모듈을 연쇄적으로 따라가며 전체 코드의 관계도 완성
    - 진입점 설정 → 의존성 분석 → 그래프 완성
  - 웹팩과 비트
    - 웹팩 - 오랜 기간을 걸쳐 검증되었지만, 코드를 수정할 때마다 전체 의존성 그래프를 분석함
    - 비트 - 파일을 미리 번들링하지 않고 브라우저가 기본적으로 지원하는 ES 모듈을 활용해 요청된 파일만 즉시 변환
- 브라우저 렌더링 과정
  1. HTML 파싱 후 돔 트리 생성
  2. CSS 파싱 후 CSSOM 트리 생성
  3. 렌더 트리 구축
  4. 레이아웃 계산 (리플로)

- 하이브리드 앱 개발에서 웹뷰와 앱이 소통하는 방법
  - 앱 방식
    - 하이브리드 앱
      - 네이티브 앱 형태를 하고있지만 내용은 웹 기술이 들어간 앱
    - 네이트브 앱
      - IOS나 안드로이드 같은 특정 운영체제를 위해 만들어진 앱
      - 기기의 모든 기능을 빠르고 완벽하게 사용할 수 있지만 플랫폼별로 따로 만들어야 한다.
    - 웹 앱
      - 브라우저에서 접속하는 웹 서비스
      - 별도의 설치가 필요 없지만 기기 기능 접근에 제약이 많다.
  - 웹뷰
    - 웹뷰는 보안상의 이유로 격리된 공간이다. 웹뷰 안의 JS는 앱의 다른 기능과 스마트폰의 고유 기능 (카메라, GPS, 연락처) 등에 직접 접근할 수 없다.
  - 네이티브 브리지
    - 브리지 중심으로 웹뷰와 네이티브는 양방향으로 통신할 수 있다.
    - 네이티브 기능을 요청할 수 있고, 네이티브가 실행 결과를 다시 웹으로 전달할 수 있다.
  - 딥링크
    - 앱의 특정 페이지로 직접 연결되는 특수한 구조
    - 외부에서 온 사용자를 네이티브가 맞이한 뒤 브리지를 통해 웹뷰 안의 목적지까지 안내한다.
  - 다이나믹 링크
    - 딥링크의 업그레이드 버전으로 사용자의 상황을 지능적으로 판단해 적절한 경로로 안내하는 링크이다. (예: 앱의 설치 여부에 따라 링크를 다르게 한다.)
- package.json 파일의 주요 필드와 역할
  - 프로젝트의 신분증이자 명세서와도 같다.
  - npm
    - npm은 전 세계 JS 개발자들이 만든 코드 패키지를 모은 거대한 온라인 저장소이다.
  - package.json은 프로젝트가 어떤 패키지를 요구하는지 정의하는 핵심 파일이다. 프로젝트의 이름과 버전, 실행 방법, 의존성 정보까지 담고 있는 일종의 프로젝트 설계서이자 npm 생태계와 소통하기 위한 공식 창구이다.
  - 핵심 필드
    - name: 패키지의 이름
    - version: 프로젝트의 현재 버전. 보통 시멘틱 버저닝(메이저, 마이너, 패치 형식으로 관리)를 사용한다.
    - description: 프로젝트를 간략히 설명하는 문장
    - main: 패키지의 진입점으로 보통 index.js를 사용한다.
    - scripts: npm start, npm test처럼 터미널에서 자주 사용하는 명령어를 미리 정의해 놓은 영역
    - author, license: 제작자 정보와 프로젝트가 어떤 라이선스 규칙을 따르는지 명시
  - package.json의 의존성 관리
    - dependencies
      - 앱 프로덕션 환경에서 동작하기 위해 반드시 필요한 패키지
      - express, react, react-dom, lodash
    - devDependencies
      - 개발 과정에서만 필요한 패키지
      - eslint, jest, webpack, vite
    - peerDependencies
      - 특정 호스트 패키지와 함께 사용될 때 그 호스트 패키지의 특정 버전을 요구한다는 것을 명시한다.
      - 자동으로 설치되지 않고 사용자에게 경고를 보내고 사용자가 직접 명시된 호스트 패키지를 설치해야 한다.
      - 주로 다른 라이브러리의 플러그인이나 애드온을 만들 때 사용한다.
      - eslint-plugin-react, @mui/material(Material-UI)
    - optionalDependencies
      - 선택적인 패키지로, 해당 패키지가 없어도 앱의 핵심 기능은 문제없이 동작해야 한다.
      - npm install 실행 시 설치를 시도하지만 특정 운영체제에서 빌드가 실패하거나 네트워크 문제로 설치가 안되어도 전체 설치 과정이 중단되지 않는다.
      - node-notifier: 윈도우, 맥, 리눅스에서 데스크톱 알림을 보내주는 라이브러리
  - package-lock.json
    - npm install을 실행할 때 메이저 버전만 고정하는 캐럿(^)이나 메이저 마이너 버전을 고정하고 패치 버전의 업데이트만 허용하는 틸드(~)를 사용하면 npm install을 사용할 때 마다 다른 버전의 패키지를 사용하게 된다.
    - package-lock.json은 이러한 위험을 해결하기 위해 현재 프로젝트에 설치된 모든 패키지와 하위 패키지의 버전까지 스냅샷 형태로 기록해 놓는다.
    - 3 가지 역할
      - 정확한 버전 고정
      - 예측하고 반복할 수 있는 빌드: 이 파일이 있으면 npm install을 실행해도 package-lock.json에 기록된 버전과 동일한 버전의 패키지만 설치된다.
      - 빠른 설치 속도: 이미 설치할 패키지의 버전과 의존성 관계를 알고 있어서 버전 범위를 계산하는 과정을 생략한다.

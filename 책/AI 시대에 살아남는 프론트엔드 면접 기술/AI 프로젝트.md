- LLM의 응답 지연 문제 사용자 경험 측면에서 해결 방안
  - 지연 시간을 사용자 경험으로 극복해야 한다.
    - 로딩 인디케이터 보다는 스트리밍을 이용한다.
    - `SSE`나 `Fetch API`의 `ReadableStream`을 사용해 구현할 수 있다.
  - 첫 단어가 나오기 전까지
    - 스켈레톤 UI와 타이핑 인디케이터를 사용한다.
  - 낙관적 UI와 중단 권한 부여
    - 사용자가 질문하자마자 응답이 올 때까지 진행 바를 보여 주되 0%에서 90%까지는 빠르게 올라가고 마지막 10%에서 천천히 움직이게 설계하면 사용자는 실제보다 빠르다고 느낀다.
    - 답변이 너무 길어지거나 진행 방향이 틀렸을 때 사용자가 직접 생성 중인 응답을 멈출 수 있어야 한다. `AbortController`를 사용해 진행 중인 스트리밍 응답을 취소할 수 있다.
- 생성형 AI 채팅 UI에서 중단 기능 구현
  - AbortController와 신호 전달
    - `Controller`: 명령을 내리는 역할
    - `Signal`: 이 명령을 전달하는 역할
  - 중단 실행
    - ‘중지’ 명령이 내려지면 `Controller`의 `.abort()`메서드를 호출한다.
    - 해당 신호를 들고 있던 모든 fetch 요청이 즉시 중단 된다.
    - 요청이 중단되면 fetch는 `AbortError`를 발생 시킨다.
- 길게 대화할 때 토큰 소모를 줄이는 컨텍스트 관리 전략
  - 슬라이딩 윈도
    - 최근 N개의 메시지만 골라 담는 방식
  - 대화 요약
    - 대화가 일정 길이를 넘어가면 이전 내용을 한 문장으로 압축해서 배경 지식으로 넘겨주는 방식
    - ‘이전 요약본 + 최신 대화 2~3건’을 묶어서 보냄
  - 로컬 스토리지 활용
    - 토큰 소모를 줄이는 기술은 아니지만 기존 컨텍스트를 즉시 복원하는 사용자 경험 연속성을 위한 필수 전략
- 이미지 Base64 인코딩과 멀티파트
  - Base64
    - Base64는 이진 데이터를(binary)를 64개의 아스키 문자로 치환하는 방식이다.
    - JSON 객체안에 텍스트로 이미지를 넣을 수 있다.
    - Base64로 인코딩하면 **원본 바이너리 크기보다 용량이 약 33% 늘어난다는 단점**이 있다.
      - 3바이트의 데이터를 표현하기 위해 4개의 문자를 사용하기 때문이다.
  - 멀티파트 (multipart/form-data)
    - 웹에서 파일을 업로드할 때 쓰는 표준 방식이다.
    - 데이터를 텍스트로 변환하지 않고 바이너리 그대로 쪼개서 보낸다.
    - 대용량 이미지나 여러 장의 사진을 보낸 때 유리하다.
    - JSON과 파일을 섞어서 보내야 하므로 서버와 클라이언트 양쪽에서 파싱 로직이 조금 더 복잡하다.
- LLM의 텍스트 응답을 구현할 때 SSE와 웹소켓
  - 데이터 흐름 특성에 최적화된 설계
    - LLM은 답변이 생성되는 동안 사용자가 추가로 데이터를 보낼 일이 거의 없는 단방향 흐름이 지배적이다.
  - SSE - 가벼운 단방향 스트림
    - HHTP 프로토콜 위에서 동작하는 단방향 통신 표준
    - 서버에서 클라이언트로 데이터를 전달하는 방식에 최적화
  - 웹소켓 - 강력한 양방향 고속도로
    - 클라이언트와 서버가 언제든 서로 데이터를 주고받을 수 있는 전이중 통신
    - HTTP로 시작하지만 연결이 확립되면 독자적인 프로토콜로 전환
  - 일반 텍스트 챗봇에 SSE를 선호하는 이유
    - 오버헤드 절감, 구현의 단순함, 안정성
  - 웹소켓을 사용해야 하는 경우
    - 실시간 음성, 멀티 유저 협업 도구, 복잡한 상호작용
- Fetch API + ReadableStream
  - 오픈AI, 엔트로픽, 구글은 SSE보다 Fetch API와 ReadableStream을 사용한다.
  | **구분**        | **SSE (Server-Sent Events)**                     | **Fetch + ReadableStream (Custom Stream)**              |
  | --------------- | ------------------------------------------------ | ------------------------------------------------------- |
  | **핵심 목적**   | 서버 → 클라이언트 일방향 이벤트 스트리밍         | 범용 이진/텍스트 데이터 연속 수신                       |
  | **연결 재시도** | **자동 재연결** 및 `Last-Event-ID` 기반복구 지원 | 네트워크 연결 단락 시 **직접 재연결 로직 구현 필요**    |
  | **데이터 포맷** | 표준ized 텍스트 이벤트 포맷 (`data: ...\n\n`)    | 완전 자유 (JSON, Binary, Plain Text 등)                 |
  | **HTTP 메서드** | 표준 `EventSource` 사용 시 `GET`으로 제한        | `GET`, `POST` 등 모든 HTTP 메서드 및 Body 전송 가능     |
  | **개발 공수**   | 브라우저 표준 API 지원으로 **매우 낮음**         | 청크 파싱, 디코딩, 버퍼링, 에러 핸들링 등 **공수 높음** |
  - 다국어 처리를 위해서 한글과 같은 다국어는 한 글자가 여러 바이트로 구성되므로 `decoder.decode(value, { stream: true })` 을 넣어야 한다.
- 스트리밍 도중 네트워크 연결이 끊겼을 때 자연스럽게 재 연결하는 전략
  - 북마크 전략
    - ‘성공적으로 받은 마지막 데이터 위치’를 기억하는 방법
    - 서버에서 각 데이터 조각을 보낼 때 인덱스를 함께 전달해서 프론트엔드는 데이터를 받을 때 마다 `lastIndex` 변수를 업데이트해 저장
  - 지수 백오프
    - ‘재 시도 간격을 2배 씩 늘려가며’ 재 연결 시도
    - 서버에 무리를 주지 않으면서 가장 적절한 타이밍에 연결을 회복

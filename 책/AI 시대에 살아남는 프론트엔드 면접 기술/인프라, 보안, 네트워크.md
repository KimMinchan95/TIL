- REST API와 RESTful API
  - REST : 분산 하이퍼미디어 시스템을 위한 아키텍처 스타일 즉, 설계 철학
  - REST API : REST 설계 원칙을 따르는 API
  - **주요 원칙**
    - 클라이언트-서버 구조 : 클라이언트와 서버의 역할 명확히 분리
    - 무상태성
    - 캐시 가능성 : 클라이언트는 서버의 응답을 캐싱하여 재사용할 수 있어야 한다.
    - 균일한 인터페이스
  - REST API는 자원을 중심으로 설계된다.
    - 무엇을 할지는 HTTP 메서드(GET, POST, …)가 담당하고, 어떤 대상인지는 URI가 자원(명사)으로 표현한다.
  - HATEOAS
    - **HATEOAS는 응답에 다음에 할 수 있는 행위의 링크를 포함해 보내 주는 것**
  ```json
  {
    "id": 123,
    "name": "홍길동",
    "major": "컴퓨터공학",
    "_links": {
      "self": { "href": "/students/123" },
      "courses": { "href": "/students/123/course" },
      "update": { "href": "students/123", "method": "PUT" }
    }
  }
  ```
- CDN
  - 전 세계에 분산된 캐시 서버를 통해 사용자가 가까운 서버에서 콘텐츠를 전달 받도록 하여 로딩 속도를 개선하고 서버 부하를 줄인다.
  - 장점 : 빠른 응답 속도, 안정성, 비용 절감
  - 단점 : 캐시 무효화 전략, 동적 콘텐츠 처리 등 고려 필요
- 브라우저 캐싱
  - Cache-Control
    - Cache-Control 헤더는 가장 기본적이고 강력한 캐싱 지시어
    - 브라우저에 이 파일은 앞으로 얼마 동안 유효하니 그 동안 서버에 다시 확인하지 않을 것임을 지시
    - public : 브라우저뿐 아니라 CDN 같은 모든 캐시 서버에 저장할 수 있다. 이 옵션이 없거나 private로 설정하면 CDN은 해당 파일을 캐싱하지 못하고 사용자 브라우저에만 저장된다.
    - max-age : 파일의 유효 기간을 나타낸다.
  - 항상 최신 파일로 유지
    - Cache-Control : no-cache
    - 캐시에 저장해 두되, 사용하기 전에 서버에 이 파일이 아직 유효한 버전인지 확인
  - ETag
    - 파일의 특정 버전을 식별하기 위한 고유한 버전 태그
    - 파일 내용이 1byte 라도 변경되면 새로운 ETag 생성
- 서버리스 함수로 API 키 관리하는 법
  - 전통적인 API 키 관리
    - 전통적인 해결 방법은 프론트엔드가 API 키 없이 백엔드 서버에 데이터를 요구하면 백엔드 서버가 저장된 API 키로 외부 서비스 API를 호출 하는 것이다.
  - 서버리스
    - 개발자가 서버를 직접 관리할 필요 없이 클라우드 제공 업체가 서버 인프라를 대신 관리해 주는 것이다.
  - 서버리스 함수로 API 키 보호
    - Next.js 프로젝트는 pages/api 또는 app/api 디렉터리에 파일을 생성하면 자동으로 서버리스 함수로 배포
    - 환경 변수를 설정한다. 민감한 API 키는 환경 변수로 관리해서 빌드 및 서버 쪽 런타임에서만 접근 가능하게 한다.
    - 서버리스 함수 내부에서 환경 변수를 사용하여 외부 API를 호출하는 코드 작성
    - 프런트엔드는 앱 내부의 API 엔드포인트를 호출한다.
  - 엣지 함수
    - 엣지 함수는 사용자와 가장 가까운 물리적 위치에서 코드를 실행한다.
    - `export const runtime = 'edge';` 1줄만 추가하면 엣지 함수가 된다.
    - 나머지 코드는 서버리스 함수와 동일하다.
  - 엣지 함수 단점
    - DB와 거리가 멀면 DB 쿼리를 호출하면, DB 바로 옆에 있는 일반 서버리스 함수보다 전체 응답 속도가 훨씬 느려진다.
    - 경량 런타임(V8 Isolate)를 사용하므로 실행 자체가 불가능한 코드가 있을 수 있다.
  - 권장 패턴
    - 엣지 함수 : DB 조회가 필요 없거나 가벼운 작업 (인증 토큰 검증, 캐싱 제어, 리다이렉트, 봇 차단)
    - 일반 서버리스 함수 : 메인 비즈니스 로직, 복잡한 트랜잭션, DB 집중 작업, 배치/파일 처리
- CORS란
  - 동일 출처 정책
    - 같은 출처에서 온 리소스만 자유롭게 공유할 수 있다
  - 출처는 3가지 요소의 조합
    - **프로토콜** : http://, https://
    - **호스트** : example.com, sub.example.com
    - **포트** : :80, :443, :3000
  - CORS
    - **서로 다른 출처 간에 리소스를 주고받도록 허용하는 공식적인 메커니즘**
    - 허용 여부를 요청을 보내는 쪽이 아니라 리소스를 제공하는 서버 쪽에서 결정한다.
- 프런트엔드 영역에서 발생할 수 있는 웹 사이트 보안 위협
  - XSS(Cross-Site Scripting)
    - **공격자가 악의적인 JS를 웹 앱에 삽입하여 다른 사용자의 브라우저 내에서 해당 스크립트가 실행되게 만드는 공격**
    - 방어 전략 - 입력값 검증과 출력값 제어
      - HTML 엔티티로 변환해 주어야함 (HTML 이스케이핑)
  - CSRF(Cross-Site Request Forgery)
    - 사이트 간 요청 위조
    - **사용자가 자신의 의지와 무관하게 공격자가 의도한 행동을 특정 웹 사이트에 요청하게 만드는 공격**
    - 방어 전략 - CSRF 토큰
      - 접속할 때마다 예측하기 어려운 임의의 문자열인 CSRF 토큰을 생성해 HTML에 숨겨 놓는다.
      - 서버의 상태를 변경하는 중요한 요청을 보낼 때 이 토큰을 함께 서버로 전송해서 검증한다.
    - 방어 전략 - SameSite 쿠키
      - 쿠키에 SameSite=Strict 또는 SameSite=Lax 속성을 설정하면 다른 도메인에서 시작된 요청에는 인증 쿠키가 자동으로 포함되지 않도록 브라우저가 마ㅏㄱ아준다.
- HTTPS
  - HTTP는 데이터가 전혀 암호화되어 있지 않은 평문 통신이었다.
    - 스니핑(중간자 공격)에 취약하다.
  - HTTPS(Hyper Text Transfer Protocol Secure)는 보안이 강화된 프로토콜이다.
    - SSL 또는 TLS 프로토콜을 통해 암호화한다.
    - SSL/TLS 핸드셰이크 과정을 겪는다.
  - 2 가지 핵심 목표
    - 기밀성(데이터 암호화)
    - 무결성(서버 신원 보증)
  - 제 3의 인증기관이 발행한 SSL 인증서를 통해 인증을 한다.
- Base64 인코딩
  - **바이너리 데이터를 텍스트 데이터로 변환하는 인코딩 방식**
  - Base64는 어떤 바이너리 데이터든 안전한 문자로 이루어진 텍스트로 변환한다.
  - Base64, 유니코드, UTF-8의 관계
    - **유니코드 문자** → **UTF-8로 인코딩** → 바이너리 데이터 생성 → **Base64로 인코딩** → 텍스트 데이터
- 웹 앱의 세션 관리와 쿠키 기반의 보안 이슈
  - 쿠키 : 브라우저가 주체가 되어 사용자 컴퓨터의 전용 공간에 저장되고 관리하는 데이터 파일
  - 세션 : 사용자의 중요한 정보를 서버에 저장하는 공간
    - 세션 쿠키를 이용해서 접속할 수 있는 세션 ID를 저장한다.
  - CSRF(Cross-Site Request Forgery, 사이트 간 요청 위조)
    - **자신도 모르게 로그인된 다른 웹사이트에 악의적인 요청을 보내도록 유도하는 공격**
    - 쿠키는 유효한 쿠키만 있으면 정상 요청으로 믿어 버리기 때문
  - SameSite의 3가지 옵션
    - Strict : 가장 엄격한 방식으로, 동일한 사이트에서 시작된 요청만 쿠키를 전송. CSRF 방어에는 가장 강력하지만 구글 검색 결과 클릭처럼 다른 웹사이트에서 정상으로 유입된 경우에도 로그인 상태가 유지되지 않는다.
    - LAX : 대부분의 브라우저에서 기본값. GET 요청과 같은 비교적 안전한 요청에는 쿠키를 허용하지만, POST/PUT 처럼 데이터를 변경하는 요청에는 쿠키를 보내지 않는다.
    - NONE : 어떤 사이트에서 시작된 요청이든 쿠키를 항상 전송. 반드시 Secure 속성을 함께 설정해야 하며 HTTPS 연경에서만 사용할 수 있다. 주로 서드 파티 쿠키를 활용한 광고 트래킹 등에 사용
- 서드 파티 스크립트를 추가할 때 발생할 수 있는 성능과 보안 위협
  - 외부 서버에서 불러오는 프로그램 코드 (구글 애널리틱스, 페이스북 픽셀, 광고 네트워크 스크립트)
  - 위험
    - 성능 저하 : 너트워크 요청 증가, 스크립트 태그를 내려받기 위한 렌더링 차단, 메인 스레드 점유
    - 보안 취약 : XSS 공격 경로, 데이터 유출, 공급망 공격(서드 파티 스크립트가 여러 파트너사의 스크립트를 함께 불러올 수 있다.)
- 웹 사이트의 로딩 성능 최적화 방법
  - **네트워크 요청 수 줄이기** : 웹 브라우저가 한 번에 처리할 수 있는 네트워크 요청의 수에 제한이 있음.
    - 코드 번들링 : 웹팩이나 비트같은 모듈 번들러를 사용하면 여러 파일을 하나로 병합해 요청 수를 줄일 수 있다.
    - 이미지 스프라이트 : 작은 이미지들을 하나로 합치고, `background-position` 속성을 이용해 필요한 부분만 잘라서 보여 준다.
  - **각 요청의 크기 줄이기**
    - 이미지 최적화
      - 압축 도구 활용
      - 압축률이 뛰어난 WebP, AVIF같은 차세대 이미지 활용
      - scrset 속성을 활용한 반응형 이미지 적용
    - 코드 최소화 : 웹팩 같은 번들러가 빌드 과정에서 자동으로 처리 해준다.
    - 텍스트 압축 : 서버에서 브라우저로 HTML, CSS, JS 같은 텍스트 기반 파일을 전송할때 Gzip이나 Brotli 방식으로 압축하면 파일 크기를 50~70%까지 줄일 수 있다.
    - 트리 셰이킹 : 실제로 사용하지 않는 dead code를 최종 결과물에서 제거한다.
- 마이크로 프런트엔드 아키텍처
  - **하나의 거대한 웹 앱을 여러개의 작고 독립적으로 배포할 수 있는 프론트엔드 앱 조합으로 구성하는 방식**
  - 특징
    - 독립적인 팀과 기술 : 검색 기능 팀은 리액트로, 상품 상세 팀은 뷰로 각자의 미니 앱을 구축할 수 있다. 다른 팀의 일정과 무관하게 독자적으로 배포할 수 있다.
    - 자율성과 책임 : 각 팀은 자신의 미닙 앱 운영에 온전히 책임을 지며, 사용자 피드백에 신속하게 대응할 수 있다.
    - 통합된 경험 : 사용자 입장에서 여러 개의 독립적인 앱을 오가는게 아니라, 하나의 완결된 앱을 사용하는 것처럼 느껴져야 한다. 이를 위해 전체 앱의 공통 컴포넌트를 관리하는 ‘셸’ 또는 ‘컨테이너’ 앱이 존재 한다.
  - 장점
    - 점진적 업그레이드와 기술 다양성
    - 팀의 자율성과 개발 속도 향상
    - 코드베이스 ㅂ분리 및 유지보수 용이성
    - 장애 격리
  - 단점
    - 앱 복잡성 증가
    - 번들 사이즈 중복
    - 통합 테스트의 어려움
    - 운영 및 배포 환경의 복잡성
  - 저장소 전략
    - 멀티레포 : 팀의 자율성이 극대화되지만, 공통 코드와 의존성 관리가 어렵다.
    - 모노레포 : 자율성을 어느 정도 유지하면서 프로젝트 전체의 일관성과 관리 효율성을 높여준다.
- 웹 브라우저가 렌더링하는 과정
  1. 도메인 이름을 IP 주소로 변환
     1. DNS(Domain Name System)는 도메인 주소를 IP 주소로 변환해 주는 역할
     2. 웹 브라우저는 자신에 캐시에 해당 도메인의 IP 정보가 저장되어 있는지 확인 → 운영체제의 캐시를 확인 → 공유기의 캐시를 조회 → 통신사의 DNS 서버에 확인 → 루트 DNS 서버부터 최상위 도메인 서버를 조회
  2. 통신을 위한 연결 수립
     1. 대표적인 전송 프로토콜 TCP(TCP는 데이터가 순서대로 오류 없이 안전하게 전달되도록 보장)
     2. TCP 연결을 위한 3-Way Handshake 과정을 거친다.(SYN, SYN-ACK, ACK)
  3. 웹 사이트 문서 요청과 수신
     1. 서버에 HTTP 요청을 보내 웹 사이트를 달라고 요청(자원의 경로, 어떤 브라우저인지, 쿠키 정보 등 다양한 메타데이터 포함)
  4. 렌더링 과정
     1. 파싱 및 트리 구축
     2. DOM 트리 생성 → CSSOM 트리 생성 → 렌더 트리 구축
     3. 레이아웃(Reflow) → 페인트(Repaint) → 합성
  | **변경 유형**       | **거치는 단계**            | **대표 속성**                                        | **성능 영향**                                   |
  | ------------------- | -------------------------- | ---------------------------------------------------- | ----------------------------------------------- |
  | **Reflow (Layout)** | Layout → Paint → Composite | `width`, `height`, `margin`, `padding`, `display` 등 | 높음 (전체 레이아웃 재계산 유발)                |
  | **Repaint**         | Paint → Composite          | `color`, `background-color`, `box-shadow` 등         | 중간 (기하학적 위치는 그대로, 픽셀만 다시 칠함) |
  | **Composite only**  | Composite                  | `transform`, `opacity`                               | 낮음/최적 (GPU 가속 활용, 메인 스레드 건너뜀)   |
- HTTP 풀링과 웹 소켓
  - HTTP 풀링
    - 과거에는 클라이언트가 주기적으로 서버에 반복적인 요청을 보내는 방식을 사용했다.
    - 새로운 데이터가 없음에도 불필요한 요청과 응답이 반복되면서 네트워크 자원이 낭비된다.
    - 이를 해소하기 위해 클라이언트가 요청을 보내면 서버는 즉시 응답하지않고 새로운 데이터가 생길 때까지 연결을 유지하는 ‘롱 폴링’ 방식을 사용했다.
  - 웹 소켓
    - 2011년 HTML5 표준으로 등장했다.
    - 클라이언트와 서버 간에 하나의 TCP 연결을 계속 유지하며 양방향으로 자유롭게 데이터를 주고받을 수 있는 통신 프로토콜이다.
    - 핸드셰이크 단계만 HTTP를 사용하고 성공하면 연결은 웹소켓으로 업그레이드 된다.
  - SSE(Server-Sent Events)
    - 클라이언트가 데이터를 수신만 하면 되는 상황일 때 사용한다.
- HTTP와 HTTP2의 차이점
  - HTTP/1.1의 문제
    - 하나의 연결에 하나의 요청과 응답만 처리한다.
  - HTTP/2
    - 2015년 등장
    - 성능 개선, 특히 응답 시간을 줄이기 위해 태어났다.
    - 멀티플렉싱 : 리소스를 프레임으로 나눠 각 스트림으로 동시에 보낼 수 있다.
    - 헤더 압축 : HPACK이라는 압축 방식을 사용해 한번 등록된 정보는 짧은 신호만으로 전달할 수 있다.
    - 서버 푸시 : 클라이언트가 HTML을 요청하면 서버는 웹 사이트에 필요할 CSS, JS 파일을 예측해 추가 요청을 기다리지 않고 미리 보내 주어 로딩 속도를 높인다.
  - HTTP/3
    - HTTP/2는 TCP 기반이어서 동시에 처리가 가능해소 TCP라는 입구 하나를 공유해야 한다. TCP 규칙상 데이터(패킷) 하나가 분실되면 다시 도착할 때까지 대기해야 한다.(TCP 레벨 HOL 블로킹)
    - HTTP/3는 UDP 기반의 새로운 프로토콜인 QUIC(Quick UDP Internet Connections)로 바뀌었다.
  - QUIC의 장점
    - 독립적인 스트림 처리 : 하나의 스트림에서 데이터(패킷)가 유실되더라도 다른 스트림에 영향을 주지 않고 계속 전송한다.
    - 연결 설정 시간 단축 : 클라이언트와 서버가 연결을 맺는 과정을 크게 단축하여 응답 속도를 더욱 향상시킨다.

- REST API와 RESTful API
  - REST : 분산 하이퍼미디어 시스템을 위한 아키텍처 스타일 즉, 설계 철학
  - REST API : REST 설계 원칙을 따르는 API
  - **주요 원칙**
    - 클라이언트-서버 구조 : 클라이언트와 서버의 역할 명확히 분리
    - 무상태성
    - 캐시 가능성 : 클라이언트는 서버의 응답을 캐싱하여 재사용할 수 있어야 한다.
    - 균일한 인터페이스
  - REST API는 자원을 중심으로 설계된다.
    - 무엇을 할지는 HTTP 메서드(GET, POST, …)가 담당하고, 어떤 대상인지는 URI가 자원(명사)으로 표현한다.
  - HATEOAS
    - **HATEOAS는 응답에 다음에 할 수 있는 행위의 링크를 포함해 보내 주는 것**
  ```json
  {
    "id": 123,
    "name": "홍길동",
    "major": "컴퓨터공학",
    "_links": {
      "self": { "href": "/students/123" },
      "courses": { "href": "/students/123/course" },
      "update": { "href": "students/123", "method": "PUT" }
    }
  }
  ```
- CDN
  - 전 세계에 분산된 캐시 서버를 통해 사용자가 가까운 서버에서 콘텐츠를 전달 받도록 하여 로딩 속도를 개선하고 서버 부하를 줄인다.
  - 장점 : 빠른 응답 속도, 안정성, 비용 절감
  - 단점 : 캐시 무효화 전략, 동적 콘텐츠 처리 등 고려 필요
- 브라우저 캐싱
  - Cache-Control
    - Cache-Control 헤더는 가장 기본적이고 강력한 캐싱 지시어
    - 브라우저에 이 파일은 앞으로 얼마 동안 유효하니 그 동안 서버에 다시 확인하지 않을 것임을 지시
    - public : 브라우저뿐 아니라 CDN 같은 모든 캐시 서버에 저장할 수 있다. 이 옵션이 없거나 private로 설정하면 CDN은 해당 파일을 캐싱하지 못하고 사용자 브라우저에만 저장된다.
    - max-age : 파일의 유효 기간을 나타낸다.
  - 항상 최신 파일로 유지
    - Cache-Control : no-cache
    - 캐시에 저장해 두되, 사용하기 전에 서버에 이 파일이 아직 유효한 버전인지 확인
  - ETag
    - 파일의 특정 버전을 식별하기 위한 고유한 버전 태그
    - 파일 내용이 1byte 라도 변경되면 새로운 ETag 생성
- 서버리스 함수로 API 키 관리하는 법
  - 전통적인 API 키 관리
    - 전통적인 해결 방법은 프론트엔드가 API 키 없이 백엔드 서버에 데이터를 요구하면 백엔드 서버가 저장된 API 키로 외부 서비스 API를 호출 하는 것이다.
  - 서버리스
    - 개발자가 서버를 직접 관리할 필요 없이 클라우드 제공 업체가 서버 인프라를 대신 관리해 주는 것이다.
  - 서버리스 함수로 API 키 보호
    - Next.js 프로젝트는 pages/api 또는 app/api 디렉터리에 파일을 생성하면 자동으로 서버리스 함수로 배포
    - 환경 변수를 설정한다. 민감한 API 키는 환경 변수로 관리해서 빌드 및 서버 쪽 런타임에서만 접근 가능하게 한다.
    - 서버리스 함수 내부에서 환경 변수를 사용하여 외부 API를 호출하는 코드 작성
    - 프런트엔드는 앱 내부의 API 엔드포인트를 호출한다.
  - 엣지 함수
    - 엣지 함수는 사용자와 가장 가까운 물리적 위치에서 코드를 실행한다.
    - `export const runtime = 'edge';` 1줄만 추가하면 엣지 함수가 된다.
    - 나머지 코드는 서버리스 함수와 동일하다.
  - 엣지 함수 단점
    - DB와 거리가 멀면 DB 쿼리를 호출하면, DB 바로 옆에 있는 일반 서버리스 함수보다 전체 응답 속도가 훨씬 느려진다.
    - 경량 런타임(V8 Isolate)를 사용하므로 실행 자체가 불가능한 코드가 있을 수 있다.
  - 권장 패턴
    - 엣지 함수 : DB 조회가 필요 없거나 가벼운 작업 (인증 토큰 검증, 캐싱 제어, 리다이렉트, 봇 차단)
    - 일반 서버리스 함수 : 메인 비즈니스 로직, 복잡한 트랜잭션, DB 집중 작업, 배치/파일 처리
- CORS란
  - 동일 출처 정책
    - 같은 출처에서 온 리소스만 자유롭게 공유할 수 있다
  - 출처는 3가지 요소의 조합
    - **프로토콜** : http://, https://
    - **호스트** : example.com, sub.example.com
    - **포트** : :80, :443, :3000
  - CORS
    - **서로 다른 출처 간에 리소스를 주고받도록 허용하는 공식적인 메커니즘**
    - 허용 여부를 요청을 보내는 쪽이 아니라 리소스를 제공하는 서버 쪽에서 결정한다.
- 프런트엔드 영역에서 발생할 수 있는 웹 사이트 보안 위협
  - XSS(Cross-Site Scripting)
    - **공격자가 악의적인 JS를 웹 앱에 삽입하여 다른 사용자의 브라우저 내에서 해당 스크립트가 실행되게 만드는 공격**
    - 방어 전략 - 입력값 검증과 출력값 제어
      - HTML 엔티티로 변환해 주어야함 (HTML 이스케이핑)
  - CSRF(Cross-Site Request Forgery)
    - 사이트 간 요청 위조
    - **사용자가 자신의 의지와 무관하게 공격자가 의도한 행동을 특정 웹 사이트에 요청하게 만드는 공격**
    - 방어 전략 - CSRF 토큰
      - 접속할 때마다 예측하기 어려운 임의의 문자열인 CSRF 토큰을 생성해 HTML에 숨겨 놓는다.
      - 서버의 상태를 변경하는 중요한 요청을 보낼 때 이 토큰을 함께 서버로 전송해서 검증한다.
    - 방어 전략 - SameSite 쿠키
      - 쿠키에 SameSite=Strict 또는 SameSite=Lax 속성을 설정하면 다른 도메인에서 시작된 요청에는 인증 쿠키가 자동으로 포함되지 않도록 브라우저가 마ㅏㄱ아준다.
